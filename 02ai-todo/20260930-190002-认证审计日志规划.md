## 目标

建立可检索、可追踪、隐私安全的认证审计能力，覆盖安全事件而不泄露密码、JWT、Cookie、Refresh Token、CSRF Token 或完整个人敏感数据。

## P0：事件模型与最小可用审计

- [ ] 定义统一 `SecurityAuditEvent`：事件 ID、事件类型、结果、发生时间、traceId/requestId、服务名、客户端类型、用户 ID（脱敏策略）、会话/令牌指纹、IP（按合规要求脱敏）、User-Agent、失败原因码。
- [ ] 定义枚举：登录成功/失败、刷新成功/失败、登出、Token 校验失败、Token 黑名单命中、CSRF 校验失败、CORS 拒绝、权限拒绝、账户锁定、配置变更。
- [ ] 在登录、刷新、登出、JWT 解析、黑名单写入/命中、CSRF/CORS 拒绝处发布事件；业务流程不能因审计存储失败而失败。
- [ ] 使用不可逆指纹（例如 SHA-256 加服务端盐）关联 Token，严禁记录原始 Token、Cookie、密码和 CSRF 值。
- [ ] 增加审计日志脱敏器，统一屏蔽 `Authorization`、`Cookie`、`Set-Cookie`、密码字段及敏感请求体字段。

## P1：存储、查询与告警

- [ ] 明确审计事件存储：初期应用日志 JSON，后续接入 Kafka/消息队列与 Elasticsearch/OpenSearch 或合规数据库。
- [ ] 明确保留期限、归档、删除和访问授权策略，满足所在地隐私与安全规范。
- [ ] 提供按时间、用户、IP、事件类型、结果、traceId 检索的受控查询接口。
- [ ] 建立异常检测规则：短时间多次登录失败、异地异常登录、Refresh Token 重放、CSRF/CORS 拒绝激增、黑名单命中异常。
- [ ] 接入告警渠道，支持阈值、去重、静默、升级和告警审计。

## P2：治理与扩展

- [ ] 定义微信、支付宝、短信、OAuth2/OIDC 等 Provider 的统一审计字段与错误码映射。
- [ ] 审计事件加入完整链路追踪上下文；网关与认证中心采用同一关联 ID。
- [ ] 制定审计数据访问 RBAC、双人审批和导出水印策略。
- [ ] 对审计链路做压测、故障降级、消息堆积与隐私泄露演练。
- [ ] 评估是否需要防篡改存储、签名链或 WORM 存储以满足合规需求。

## 当前设计原则

1. 审计旁路、异步、可降级；不得阻断认证主链路。
2. 先定义事件与脱敏规范，再接入存储和告警。
3. 认证信息仅保存最小可用元数据和不可逆指纹。
4. 网关与服务端不得信任客户端伪造的用户身份请求头。
